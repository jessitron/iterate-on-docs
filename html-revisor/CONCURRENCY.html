html-revisor: concurrent changes

What Claude understands so far about making the page hold up while you and an agent change it at once. A first draft to correct, not a design.

What the project is for

Your agents generate HTML documents. html-revisor makes the rendered page the place where you correct them: click an element, leave a directive or edit its content as markdown.

Everything lands in the HTML file itself. No sidecar, no browser state. The agent reads the file, acts, and removes the directive.

What this change is for

Turn-taking makes you wait. Replies showed the better shape: many small threads at once, the page as the conversation. Run 01 had 16 directives on the page against one chat message.

So two writers on one page is the main use. Today's design treats it as an exception.

Three facts make the trouble: a save that meets a changed element is refused and asks for a reload; the tab can't show content it didn't save; the agent has no way to change content through the server.

What broke in run 01

Erased Your directive saved between the agent's read and its write. The agent's write won. It was never in a commit.
Lost in conflict Your box was open on a paragraph the agent changed. 25 refused saves, and your directive never reached the file.
Echo A box opened before an agent edit announced the agent's text as your revision. Six times.
No sign A box open across an agent edit doesn't show that its element changed.

You said these are symptoms from one run, and the problems are much bigger.

How this differs from concurrent editing out in the world

Google Docs, CRDTs Here
The record The system owns the store and sees every operation. A plain file. The agent's Edit tool, the formatter, and a checkout all write it. The server sees states, not operations, unless the agent goes through it.
The writers Alike: people typing. Unalike. You change one element through a box. The agent reads, thinks for a minute, and may rewrite a whole diagram, so its base is always old.
A lost change Costs the same for anyone. The agent can read again and redo. Your typed words can't be regenerated. The rule can be lopsided: the agent gives way, and you lose nothing.
The grain Keystrokes and cursors. Elements. The hard part is identity: an agent rewrite can drop or copy element IDs, and directives hang on them.
Intent Edits are independent. Edits answer each other: an agent edit is often the answer to a directive. Who made a change matters, and the echo is that going wrong.
Awareness Cursors and presence. The agent hears you through Announcements. You have nothing that shows what the agent changed.
Size Many users, networks that split, offline. One human, one machine, one server. A server that puts changes in order is enough; I doubt this needs a CRDT.
Instructions You can't tell users how to edit. The skill tells the agent how to edit. It will still fumble now and then, so disk writes need a safety net.

A tension in the docs

REPLY-DESIGN decided that the server should be the only process that writes the live file. The yak “Rethink who edits the live file” lists that as one of three options. I count it as open.
