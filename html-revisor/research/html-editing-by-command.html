HTML editing by command

Research for html-revisor, 2026-11-12. Question: which elements should the agent's command (change.mjs) address, with which operations, and how should positions and identity work? Grounded in README.md ("The agent's command"), CONCURRENCY.html (#model, #interface, #where-marks), SCOPES-DESIGN.html's Decided tables, and domain/scopes.mjs, identity.mjs, agent-change.mjs, notices.mjs.

The short answer

  • The field splits this into two questions. What can be named (identity, addressing). What may go where (the schema, or in HTML, the content model). Scope answers a third question: what a human can pick. Keep the three apart.
  • Address by stable ID, not by path or offset. Every system that edits while someone else edits does this, or pays for transforming positions. html-revisor already does it.
  • The set of addressable elements should be the elements with an ID, which notices.mjs already calls a unit. Today that is scopes, hr, svg elements, and checkboxes. The command already takes any of them; the README says "scope". Add tr to the units. Do not add phrasing elements (strong, em, code) or text nodes.
  • The four operations (replace, add, remove, move) are the classic tree edit set: update, insert, delete, move. Keep them. Consider a fifth, a string edit inside one unit, shaped like str_replace.
  • Check every change against the HTML content model and refuse what breaks it. Do not repair. This is what ProseMirror steps and the Google Docs API do.

The edit-operation vocabulary is old and stable. Zhang and Shasha (1989) use insert, delete, relabel. Chawathe et al. (1996) add move and call relabel update. GumTree and XyDiff use insert, delete, update, move. html-revisor's replace, add, remove, move map to update, insert, delete, move.

What each system chose, and why

DOM mutation APIs

  • Node model: element, text, comment, and more. Every node is addressable in memory by reference. Nothing is addressable across sessions except by an id attribute, which the author maintains.
  • Operations: before(), after(), append(), prepend(), replaceWith(), remove(). insertAdjacentHTML names four positions: beforebegin, afterbegin, beforeend, afterend.
  • The DOM had no real move. appendChild of an attached node is remove then insert, and state is lost. moveBefore() was added for "state-preserving atomic move" (shipped in Chrome 133). Lesson: a move that keeps identity is its own operation. Delete-plus-insert is not the same thing.
  • The DOM API itself does not enforce the content model. The parser does. A <div> inside a <p> survives a DOM call and breaks on the next parse. This is why html-revisor reparses and compares.

XML Patch (RFC 5261) and XUpdate

  • Three operations: add, replace, remove. No move; the RFC leaves it to a future extension.
  • Target by sel, a subset of XPath 1.0. Any node type is a target: element, attribute, text, comment, namespace, processing instruction.
  • pos on add: before, after, prepend; with none, append as last child.
  • The selector must match exactly one node, or the patch fails.
  • The root element can't be removed or get a sibling. Same rule as html-revisor's body.
  • XUpdate (XML:DB, 2000) has insert-before, insert-after, append, update, remove, rename, all addressed by XPath.
  • Why XPath: XML had no identity layer. The cost: a positional path like /doc/p[3] goes stale the moment someone inserts a p above it.

JSON Patch (RFC 6902)

  • Six operations: add, remove, replace, move, copy, test. Addressed by JSON Pointer (RFC 6901): a path with array indexes.
  • test is the precondition: the patch fails unless a value matches. It plays the role of html-revisor's version.
  • Array indexes shift. JSON Patch assumes one writer, or a lock around the patch.

Tree diff algorithms

Algorithm Operations Identity Note
Zhang-Shasha (1989) insert, delete, relabel None; finds the cheapest mapping Ordered trees, O(n^4) worst. No move: a moved subtree costs a delete plus an insert of every node.
Chawathe et al. (1996) insert, delete, update, move Matching by label and value Defined the edit script most later tools emit.
XyDiff (ICDE 2002) insert, delete, update, move Uses ID attributes first, then XIDs, persistent node IDs Near-linear. Matching by ID attributes first is what html-revisor's data-hrv gives for free.
X-Diff (ICDE 2003) insert, delete, update Node signatures Unordered trees: order carries no meaning, so no move.
GumTree (ASE 2014) insert, delete, update, move Top-down match on identical subtrees, then bottom-up on containers Optimal diff with moves is NP-hard; GumTree uses a heuristic. html-revisor's reconcile is a small cousin: identical siblings first, then alike ones with the same tag.

Lesson: diffing guesses identity. When you can carry identity in the document, you skip the guess. Diff remains the fallback for content that comes back without IDs, which is what reconcile does on replace.

Patterns across this table:

  • Inline formatting is not a node in the editors built for collaboration. ProseMirror, Peritext, Quill, and Google Docs treat bold and links as marks on text. Nobody addresses a strong by ID.
  • Persistent IDs live at block granularity: Notion blocks, Jupyter cells, Gutenberg blocks. Below that, systems use offsets inside the block.
  • The schema refuses; the step does not repair. Repair lives in a higher layer that the user's intent drives.
  • Tables are the hard case everywhere. Google Docs has row and column operations of their own and forbids row deletion by range.

OT and CRDTs for trees, and move

  • OT transforms positions through concurrent operations. It needs a transform for every pair of operation types. Tree OT with move is hard to get right; the literature has many broken proofs.
  • CRDTs give each node a unique ID, so positions never shift. Kleppmann et al., "A highly-available move operation for replicated trees" (IEEE TPDS 2021): nodes are named by unique ID; move is the core operation; concurrent moves that would make a cycle are undone and redone in timestamp order. Two concurrent moves of one node: one wins, the node does not duplicate.
  • Kleppmann, "Moving elements in list CRDTs" (PaPoC 2020): delete plus insert duplicates an element when two replicas move it at once. Move must be its own operation.
  • html-revisor has one server taking every change in turn (oneAtATime). It does not need OT or a CRDT. It needs what they agree on: IDs, not positions, and a move that keeps identity. It has both. The cycle check (a scope can't move inside itself) is the serial form of Kleppmann's rule.

Agent-facing editing interfaces

Tool How it addresses Precondition
Anthropic text editor tool (str_replace) An exact string that must occur once in the file The match. Zero or several matches: error, "provide more context to make a unique match."
Aider edit formats whole file; SEARCH/REPLACE blocks; a simplified unified diff The search text must match
Serena (MCP, LSP-backed) Symbol name: replace_symbol_body, insert_before_symbol, insert_after_symbol The symbol exists
html-revisor change.mjs Element ID; before / after / into Version on replace and remove
  • Agents edit text, not trees. Content-addressed edits (the old string) work for them: the model copies what it sees. Line numbers and offsets fail, because the model miscounts and the file moves.
  • A unique-match edit carries its own precondition. If the old string is gone, someone changed it. That is optimistic concurrency at the size of the edit, not the size of the element.
  • Serena is the closest analog. Symbols are the addressable unit for code, the way scopes are for documents. Its operations are replace body, insert before, insert after. Serena has no symbol-level move.
  • Whole-unit replace costs output tokens in proportion to the unit. A 4 KB section replaced for one word is the agent's version of aider's "whole" format.

Which elements should be addressable

Scope, unit, element: three sets

Set Question it answers Where it lives
element What HTML has. Industry term. The parser
unit (an element with an ID) What can be named across edits. What a notice marks. What the command addresses. identifiable() in identity.mjs; named "unit" in notices.mjs
scope What a human picks to direct or edit as markdown. scopeElements in scopes.mjs, plus the client's data-no-revise rule

Every scope is a unit. Not every unit is a scope: hr, svg shapes, and checkboxes have IDs but are not scopes. The command's code already takes any unit: elementById finds any data-hrv. The README and CONCURRENCY.html call the target "the scope". The code is ahead of the words.

Recommendation: the command addresses units. Write that in the README. The human picks scopes; the agent names units. Scope stays the human's word. If "unit" doesn't fit as a public word, the field's neutral word for an addressable node is target (what you act on) and anchor (what you place beside).

Case by case

Element kind Today If addressable If not Recommendation
Block (section, p, h2, div) Scope, unit The common case. Works. n/a Unit. No change.
List item li, dt, dd Scope, unit Add after an li with an li works. A p after an li is refused by PARENTS. Every item edit replaces the whole list, and any edit to any item makes it stale. Unit. No change.
Table row tr Not a unit. "Replace the table." Add, remove, move, replace one row. The notice can mark one row (CONCURRENCY #where-marks proposes this). Reconcile has to keep row IDs across a markdown save of the table. A one-row change replaces the table. The table's version covers every cell, so your edit to any cell makes the agent's row add stale; and add has no version, so it can't even say so. The table's notice is the whole table. Make tr a unit, not a scope. Same standing as hr. Matches Google Docs, which gives rows their own operations.
thead, tbody, tfoot Not units IDs on parser-made wrappers the agent never wrote. "add into table" with a tr is refused: table holds tbody, not tr. Not units. Let add into <table> with rows land in the last tbody, a normalization the formatter already does in spirit (canonical form puts rows in thead/tbody). Or refuse with "add into the tbody, or after a row". See open question 3.
Cell td, th Scope, unit Replace a cell's content works. Moving a cell to another row is legal HTML and wrecks the column. n/a Unit. Consider refusing a move of a cell out of its row.
Link a, image img, span Scope, unit Replace a link works. Add after a link puts inline content in a sentence. Move a link into another paragraph works. Edits to links go through the paragraph. Unit, since they are scopes and carry directives. Inline adds are the risky ones: an add after <a> with a <p> must be refused (the reparse check catches it).
Phrasing: strong, em, code, br Not units Every bold word gets an ID. Markdown saves rebuild them, so IDs churn. read output fills with IDs. Notices get too fine. Change it by replacing its block. The field agrees: these are marks, not nodes. Not units.
Text node Not addressable Can't hold an attribute. Would need offsets or character IDs (Peritext), which an agent can't count. Text edits go through the block, or through a string edit (below). Never a target. Reach text through a string edit inside a unit.
svg and its elements Every svg element is a unit; svg text is a scope Fine-grained: move a shape, relabel one text. HTML from the agent is parsed as svg inside an svg. A big diagram carries hundreds of IDs, all in read output. A one-label change replaces the whole drawing. Keep as is. Agents redraw diagrams whole more often than they nudge a shape; replace on the svg covers that, and reconcile keeps IDs on what came back the same. Watch the ID noise in read.
hr, checkbox Units, not scopes Remove an hr, add before it: fine. into is refused (void). n/a Unit. No change.
body Unit; no replace, remove, move, before, after n/a n/a Same as RFC 5261's root rule. Keep.
Inside data-no-revise Units; the human can't pick them The agent marked them; the agent may change them n/a Addressable. The mark limits the human, not the agent.
head, script, style Not units The agent could break the page's behavior. Edit the file. Not units. Out of scope for the command.

What goes wrong either way

Choice What breaks
Only scopes are addressable Rows can't be named. Coarse targets mean more false conflicts: a change to one cell makes the whole table's version stale. Bigger replaces cost more tokens and more reconcile guessing. Notices mark too much.
Every element is addressable IDs on strong and em churn on every markdown save. Parser-made elements (tbody) get IDs nobody wrote. read output gets noisy, and the agent copies IDs into places they don't belong. Notices get too fine to read. Text nodes still can't be named, so the set is never "every node".
Units, with tr added (recommended) Two words to teach: scope (pick) and unit (name). Reconcile has to pair rows across a markdown save of a table. One more ID kind in identifiable().

Which operations

Operation Field name Today Recommendation
replace update (with relabel) Version required. Root keeps the ID whatever its tag. Reconcile pairs the children. Keep. Keeping the ID through a tag change (p to h2) is Zhang-Shasha's relabel, and it keeps the thread on it.
add before / after / into insert No version. into means last child. Keep. The positions match DOM insertAdjacentHTML, RFC 5261 pos, Notion position, Serena's insert-before/after. Missing: first child (RFC 5261 prepend, DOM afterbegin). Today the agent writes "before <first child>", which fails when the parent is empty or its first child is bare text.
remove delete Version required. Threads move to the holder. Keep. The thread rule is html-revisor's answer to the tombstone.
move move No version. Carries ID, content, threads. Keep. It is the identity-preserving move that DOM moveBefore(), Chawathe, and Kleppmann each treat as its own operation.
(new) edit text in a unit str_replace, scoped None Consider edit <id> < {old, new}: an exact string, once, inside one unit. The match is the precondition, so no version. Small changes stop costing whole-scope replaces, and stop going stale when the human edited a different sentence of the same scope. The result must reparse to the same structure, as today.
(not recommended) set attribute set_node, XML Patch on @attr None; replace does it Leave out. Replace covers it, and attribute-only changes are rare in these pages.
(not recommended) copy JSON Patch copy None Leave out. Add with new HTML does it, and copied IDs get retired anyway.

Preconditions

Replace and remove carry a version. Add and move carry none, on the reasoning that they change no scope's content. Two cases that reasoning misses:

  • Add after a paragraph the human just rewrote. The anchor still exists, so the add lands, next to text that may no longer fit it. Notion and Yjs insertAfter make the same choice. ProseMirror would map the position and land it too. The field accepts this; the notice is the safety net.
  • Move into a section the human just deleted. The anchor is gone; the move is refused. Correct.

An optional version on add and move (the anchor's, or for into, the parent's) would let a careful agent ask for the strict form. JSON Patch's test is that idea as a separate operation.

Schema: refuse, don't repair

html-revisor checks three things: PARENTS (where an element may sit), CHILDREN (what a list, table, or row may hold), and a reparse that must give back the same text. That is a content-model check, the job a ProseMirror schema does. ProseMirror's step fails; Google Docs refuses; html-revisor refuses with a reason. The agent can read the reason and retry. Repair, where it happens (ProseMirror's fit, Slate's normalizers), belongs to a layer where the user's intent is known. An agent's command has no such layer.

Name it. The two tables plus the reparse are the page's content model. Pulled into a domain module of its own (say domain/content-model.mjs), it gets one home, tests by case, and a name that matches the WHATWG spec's. The tables cover lists, tables, and definition lists. The reparse catches the rest (a div in a p). One known gap the reparse can't see: an element HTML allows but the page's own rules don't, such as a scope under 4 KB that grows past it through an add.

Positions and identity

  • Address by ID. Paths (Slate, JSON Pointer, XPath positions) and offsets (ProseMirror, Quill, Google Docs) shift when anyone inserts above. They need a single writer, a transform, or a mapping. html-revisor has a human and an agent writing at once, with no transform layer. IDs are right.
  • Persist IDs in the file. Lexical keys are not serialized and come back new on load. That works for one editor session; it fails for an agent who reads now and writes in ten minutes. Notion, Jupyter, and XyDiff's XIDs persist. So does data-hrv.
  • Positions relative to an anchor: before, after, into (last), and maybe first. This is the vocabulary of DOM, RFC 5261, Notion, and Serena. It is also what an agent can say without counting.
  • ID rules on a change (today): an ID kept from inside the replaced unit stays; an ID from elsewhere, made up, or written twice comes off; an ID missing from content that came back the same is restored by reconcile. This follows XyDiff: trust explicit IDs first, then match by content.
  • ID through a move: kept. Through a copy: retired, every copy gets a fresh one. Through a tag change on replace: kept by the root.

Recommendations, in order

  1. Say "unit" (or "element with an ID") for what the command addresses. Update README's "The agent's command" and CONCURRENCY.html. Scope stays the human's word. This is a words change; the code already does it. It is a Contract question if the skills in iterate-on-docs say "scope" for the command's target.
  2. Give tr an ID, as a unit and not a scope. Reconcile rows across a table's markdown save. Then "a table row has no ID: replace the table" goes away. CONCURRENCY #where-marks recommends the same for notices.
  3. Keep phrasing elements and text nodes out. Reach them through their block, or through recommendation 5.
  4. Pull the content model into its own domain module and name it. Keep refusing.
  5. Consider a scoped string edit, edit <id> with an old and a new string, the match as its precondition. It lowers token cost and false conflicts on big scopes.
  6. Consider "first" as a position, or document "before <first child>" and its gap.
  7. Consider an optional version on add and move for agents that want the strict form.

Open questions for Jess

  1. Should the public word for what the command addresses be "unit", "element", or something else? The code and notices say unit; the README says scope.
  2. Should tr become a unit now, with the notice work in CONCURRENCY #where-marks, or as its own yak?
  3. For add into <table> with rows: land them in the last tbody, or refuse and say where to add?
  4. Do you want a scoped string edit (edit <id>) for the agent? It would be a minor release and a skill update in iterate-on-docs.
  5. Should a cell be allowed to move out of its row?
  6. svg: keep an ID on every shape, or only on the svg and its text labels? Fewer IDs means less noise in read, and fewer things the agent can name.
  7. Should add and move take an optional version, or is the notice enough of a safety net?
