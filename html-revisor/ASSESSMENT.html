Architecture and code quality

An assessment of html-revisor as of 2026-10-25: 4,300 lines of our own code, 239 tests in 8 seconds. What holds up, where the weight sits, and five recommendations.

Verdict

The bones are good. The tier rules are executable, the domain is pure, the file is the only source of truth, and the concurrency model fits on an index card. The trouble is weight distribution: three files carry most of the change, and each holds more than one idea.

Holds up Strains
  • test/architecture.test.mjs enforces tiers, purity, and no cycles. Rare, and worth more than any diagram.
  • One writer, one turn per file (oneAtATime), optimistic checks by base. Simple and correct.
  • Round-trip tests on real pages and seeded generated edits catch fidelity bugs no example would.
  • Comments say why. Names come from the domain: directive, scope, base, thread, spill.
  • Telemetry on every step, with Honeycomb queries documented.
  • The save rules live in server.mjs, Tier I, the most-changed file.
  • domain/scopes.mjs is four modules in one, and identity.mjs reaches into it.
  • client.js is a whole app in one file, with no tiers; its sync state is 20 loose variables beside DOM code.
  • The wire protocol has three written copies and no single owner.
  • No context map: the agent writing the file around the server is a boundary nobody drew.

Recommendations

# Change Payoff Effort Mountain
1 Move the save rules into the domain high medium fidelity
2 Split scopes.mjs by idea high low fidelity
3 The client is an app: give it tiers and a protocol high high fidelity, ergonomics
4 One owner for the wire protocol medium low upkeep
5 Small cleanups low low upkeep

1 · Move the save rules into the domain

applyChange in server.mjs is 80 lines, and most of them are domain rules: a base that doesn't match is a conflict, a spill that moved is a conflict, a reply since is a conflict, a grown scope loses its markdown. Tier I decides all of that today. That is why server.mjs changed in 44 commits since September, more than any other file.

  • Tests of conflict rules move from acceptance (HTTP, temp files) to plain function calls. Faster, and closer to the rule.
  • Telemetry: the step port is in place. tabStateOf in domain/served-page.mjs takes step(name, fn), and server.mjs passes the adapter from interface/telemetry.mjs; CLAUDE.md and README document the pattern. revision.mjs takes the same port, and the spans OBSERVABILITY.html queries stay.
  • Makes Rethink who edits the live file cheaper: whatever the answer, it needs the rules in one place.

2 · Split scopes.mjs by idea

806 lines, four ideas, and most open fidelity yaks land here: link pairing, tables, inline fallback, button text, blank lines. identity.mjs imports canonicalHTML, isBlock, and hasAttrs from it. That import is not circular: scopes.mjs imports only canonical, likeness, and markdown-it, and the architecture test checks for cycles. But it puts the module that "knows nothing of IDs" under the one that assigns them, for helpers that are about canonical form, not scopes. Two modules each define a BLOCK set, and the sets differ: canonical's means "laid out on its own line", scopes' means "a block you can pick".

Mechanical, covered by the round-trip tests, and it lets two fidelity yaks run in parallel without colliding in one file. Done, on main: scopes.mjs (100 lines, kinds and picking), to-markdown.mjs (252), from-markdown.mjs (367), scope-report.mjs (77), and canonical.mjs took the canonical-form helpers. The two markdown halves need each other: the writer checks each piece by reading it back. So to-markdown imports from-markdown, and the shapes both use live in from-markdown. scopeOf went to the report module, since it calls the writer.

3 · The client is an app: give it tiers and a protocol

client.js is the largest file, 1,474 lines, and a whole little app: a view, a sync engine, a server conversation, its own telemetry. It has none of the layering the server has. Its hardest part has no shape: twenty top-level variables that together are a state machine for "what the file holds, what this tab typed, what's in flight, what came back". Every client test drives it through a linkedom tab with a faked focus model and a fast clock, and four CLAUDE.md gotchas are about that harness.

Give it the same three tiers, under the same architecture test, and one protocol module that both sides import.

The twenty variables today, grouped by what they mean. Above: what moves to the client's domain. Below: where each group lands.

  • No build step needed. Serve the client as ES modules from a dot path, /.hrv/client/…, the way /.hrv/spans takes the browser's spans, and load it with one <script type="module">. Then the architecture test reads its imports like any other module's. The published pages on GitHub Pages carry no client, so nothing changes there.
  • domain/protocol.mjs is the shared kernel in DDD terms: the one piece both contexts own, kept small and changed together. It's how recommendation 4 lands, and the server serves it to the browser under the same dot path.
  • The client's domain is where the yaks urgent: notify if the server is down, Live notice shows content edited on disk, and A half-typed save can drop a directive land. They get cheaper to build and to test.
  • Cost: test/client.test.mjs evaluates one inlined script today. Its tab has to load modules, or most of its tests move down to plain domain tests and the tab keeps a few end-to-end ones. The second is the better trade.
  • Largest effort here. Worth a design pass in REPLY-DESIGN style first, and it goes after recommendation 1, which settles the server side of the protocol.

Is there enough test coverage to do it safely?

Yes, for the sync engine, the part that moves to client/domain/. The server side of every case is covered: 46 acceptance tests over real HTTP, 412s and spills included. The tab has 26 tests: 14 in client.test.mjs on threads, the docket, and focus, and 12 in client-sync.test.mjs, one or more for each sync row below.

The sync tests are characterization tests, in the tab harness both client test files share, client-lib.mjs. They pin what the client does today, and they're end-to-end, so they keep passing while the code moves under them. Once the domain exists, some of them move down to plain node tests. Layout and the browser's undo stay manual: linkedom has neither, and the view code moves least. One gap they pinned is a yak: a markdown save in another tab reads as "the page changed on disk" here, and that element refuses saves until a reload.

Brief for the agent who writes them

  1. Read CLAUDE.md's gotchas on the client test tab first: the fast clock, the faked focus, waiting on the tab's DOM, comparing elements with assert.ok(a === b), closeAllConnections.
  2. One tab test per sync and box-session row in the table above. README's "Manual client checklist" says what each should do; name the checklist line in the test.
  3. Pin what happens now. Don't change client.js or server.mjs. A bug found gets a test pinning today's behavior, a comment naming the bug, and a yak tagged @mountain:fidelity.
  4. What the harness can't reach (layout, real focus): say so in the report, don't fake it.
  5. New file test/client-sync.test.mjs, with the harness pulled out of client.test.mjs into a lib, so the files run side by side. Time each file before and after; update TESTING.html if the bars change.
  6. Worktree, a commit per group of tests, rebase, full suite with --test-reporter=tap, fast-forward main, remove the worktree. Mark the yak done; don't push or yx sync.
  7. Report: rows covered and by which tests, bugs and their yaks, what couldn't be reached, suite time before and after, side effects outside the repo.

4 · One owner for the wire protocol

The PUT, POST, and SSE shapes are written out three times: README's Design section (one bullet runs past 600 words), the comments over putChange and postDone, and the 400 error messages, which describe the shapes by hand. Each change to the protocol touches all three, plus client.js.

  • The shapes and their validators go in domain/protocol.mjs, each validator beside the shape it checks, with its error message. The server's revision.mjs (recommendation 1) and the client (recommendation 3) both import it.
  • README keeps one short table of the shapes and links the module, the way it links SCOPES-DESIGN for scope rules. The Design section gets bullets a person can read in one breath.

5 · Small cleanups

  • server.mjs imports formatFiles from formatter.mjs, Tier I to Tier I. The rule allows it, but it makes one entry point a library of another. Fine as is; name it in the architecture test's comment so it reads as chosen.
  • parse(onDisk) then assignIds, three times in server.mjs. Folds into readRevision with recommendation 1.
  • The constants STAND_IN, STOPS, FROM_MARKDOWN sit at the end of scopes.mjs, after the code that uses them. They move with the split.
  • Three fingerprints share the word "base" and its cousins: version (the file), base (an element), thread base (a thread). Clear in the code; worth one line in the context map so the tab and agent sides keep them apart.

Leave these alone

  • oneAtATime: twelve lines, and it makes the whole concurrency story true.
  • The architecture test. Extend it when the split lands (a rule for "report code stays out of the core scope module", if it earns one), but don't loosen it.
  • Files as the only truth, and the right to rewrite them. It's what keeps the tool small.
  • The vendored bundles. They cost 700 KB of repo and buy running behind a proxy.
